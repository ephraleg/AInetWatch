# AINetWatch.com — Product Specification

**Version:** 1.0  
**Date:** August 11, 2026  
**Status:** Planning  
**Related document:** `docs/MASTER-PLAN.md`

---

## 1. Product Definition

AINetWatch is a high-density AI news intelligence wire.

The product should allow a reader to:

1. Scan a large number of AI developments quickly.
2. Understand the basic significance of a story without leaving the site.
3. Decide whether the story is worth reading.
4. Click directly to the original reporting.
5. Return later to find new developments.

The homepage should remain a **wire**, not become a conventional news-card or magazine layout.

---

# 2. Homepage

## 2.1 Primary layout

The homepage should contain:

1. Masthead
2. Optional small advertising position
3. News wire
4. Additional advertising positions where appropriate
5. Footer

The news wire is the dominant element.

## 2.2 Story presentation

Each story should display:

- Headline
- Source
- Category
- Publication/update time where appropriate
- Tooltip/summary interaction

Preferred visual structure:

    HEADLINE
    Source · Category

Avoid:

- Large thumbnails
- News cards
- Excessive borders
- Large colored category badges
- Decorative graphics
- Excessive whitespace between individual stories

## 2.3 Information density

The design objective is:

> More useful information per screen, not more decoration per screen.

A reader should be able to scan many stories without excessive scrolling.

# 3. Masthead

**AI NETWATCH**

**AI News, Now.**

- Strong visual hierarchy
- Compact vertical footprint
- Responsive on mobile
- Cypher branding
- Link to homepage
- Appropriate semantic heading structure

# 4. Story Categories

Primary categories:

- Models
- Research
- Security
- Governance
- Business
- Infrastructure
- Applications

Category information should be subtle.

Example:

    OpenAI announces new model architecture
    Reuters · Models

## Tooltip

Categories may be displayed more prominently inside the tooltip.

## Future

Support secondary categories internally without requiring them to appear on the homepage.

---

# 5. Headlines

## 5.1 Headline source

Every story must identify whether the displayed headline is:

- Original source headline
- Edited AINetWatch headline

## 5.2 Editing rules

An edited headline may improve:

- Clarity
- Brevity
- Readability
- Consistency
- Search relevance

It must not introduce:

- Unsupported facts
- New claims
- False certainty
- Unsubstantiated causality
- Sensational conclusions

## 5.3 Headline alternatives

ANWU may generate multiple headline alternatives.

The human reviewer selects the final headline.

---

# 6. Source Attribution

Every story must clearly identify its source.

Example:

    Headline
    Reuters · Security

Clicking the story should take the reader to the original source.

AINetWatch should not obscure or unnecessarily delay the outbound link.

Where multiple credible sources report the same story, additional sources may be attached to the story object.

---

# 7. Tooltip System

## 7.1 Purpose

The tooltip exists to answer:

> "Do I want to click this?"

It should not replace the original article.

## 7.2 Desktop interaction

Primary interaction:

**Hover over headline → display summary.**

The tooltip should disappear when the pointer leaves the relevant interaction area.

## 7.3 Mobile interaction

Mobile devices do not have reliable hover behavior.

Use:

**Tap summary indicator → display summary.**

The implementation must not make it unclear how to access the original article.

## 7.4 Tooltip structure

Preferred structure:

    [Cypher]

    HERE'S THE SUMMARY

    • What happened
    • Why it matters
    • Who/what is affected
    • Important context

    Category

## 7.5 Summary length

Normal:

- 2–4 bullets

Maximum:

- 5 bullets

Bullets should be short phrases or short sentences.

## 7.6 Summary quality

Summaries should:

- Be factually supported by the source
- Avoid speculation
- Explain significance
- Avoid unnecessary repetition
- Avoid copying source text
- Avoid replacing the source article

## 7.7 Summary generation

Summaries may be generated by AI but must pass the human approval process before publication.

# 8. Mobile Experience

The mobile version must be treated as a primary product, not a reduced desktop version.

Requirements:

- Responsive layout
- Readable base font size
- Adequate tap targets
- No horizontal scrolling
- Appropriate line length
- Touch-friendly tooltip interaction
- Easy outbound navigation
- Compact masthead
- Footer remains accessible

The mobile user must be able to scan stories quickly.

---

# 9. Archive

The archive should retain published stories.

Requirements:

- Date navigation
- Monthly navigation
- Category filtering
- Search
- Links to individual source articles
- Consistent story presentation

The archive is a permanent content repository.

Stories should not automatically disappear merely because they are more than 10 days old.

---

# 10. Category Pages

Create crawlable category pages:

- `/models/`
- `/research/`
- `/security/`
- `/governance/`
- `/business/`
- `/infrastructure/`
- `/applications/`

Each page should contain:

- Category title
- Brief description
- Current stories
- Recent stories
- Historical stories
- Internal links
- Relevant related categories

Pages should be statically generated where practical.

---

# 11. Search

Search should operate against a generated static search index.

Search fields:

- Headline
- Source
- Category
- Date
- Relevant keywords

Required filters:

- Date
- Source
- Category

Search should not require a database for the initial implementation.

---

# 12. RSS

Generate an RSS feed from the approved story dataset.

Requirements:

- Include approved stories
- Include headline
- Source
- Publication date
- Original URL
- Appropriate description/summary
- Validate feed
- Add RSS discovery metadata

# 14. About Page

The About page should explain:

- What AINetWatch is
- Its purpose
- Its independent aggregation model
- How stories are selected
- How summaries are produced
- Human editorial review
- Source attribution
- Corrections
- Contact/Send a Tip

The page should also provide useful organizational and topical context for search engines.

# 15. Editorial Standards

AINetWatch should maintain a dedicated Editorial Standards page.

It should explain:

- Source selection
- Headline standards
- Attribution
- AI-assisted processing
- Human approval
- Duplicate handling
- Corrections
- Updates
- Advertising disclosure

---

# 16. Corrections and Updates

The product must support corrections.

A story may contain:

- Published timestamp
- Updated timestamp
- Correction flag
- Correction note
- Source update status

Corrections should be reflected in both the underlying data and rendered page.

---

# 17. Advertising

Reserve three positions:

1. Small top banner
2. Mid-page
3. Lower-page

Requirements:

- Ads must be visually distinct
- Ads must not resemble editorial content
- Ads must not interfere with scanning
- Ads must not significantly obstruct mobile content

Advertising should initially remain disabled.

Activation should occur only after sufficient traffic exists to justify testing.

---

# 18. Dark Mode

Support:

- System preference
- Manual light/dark selection if practical
- Readable contrast
- Consistent tooltip styling
- Consistent advertising treatment

Dark mode is lower priority than:

1. Indexability
2. Mobile usability
3. Typography
4. Archive
5. Search
6. Tooltips

---

# 19. Performance

The site should prioritize:

- Fast initial HTML response
- Minimal JavaScript
- Minimal dependencies
- Optimized CSS
- Efficient static assets
- Fast mobile loading

Primary news content should exist in the initial HTML.

JavaScript should enhance the experience rather than render the fundamental news wire.

---

# 20. Publishing Architecture

Preferred architecture:

    Candidate Queue
          ↓
    Human Approval
          ↓
    Approved Queue
          ↓
    Static Build
          ↓
    Generated HTML
          ↓
    GitHub
          ↓
    Cloudflare

The approved dataset should generate:

- Homepage
- Archive
- Category pages
- Topic pages
- RSS
- Sitemap
- Search index
- Metadata
- Structured data

---

# 21. Analytics

Track:

- Unique visitors
- Returning visitors
- Stories per visitor
- Outbound clicks
- Outbound CTR
- Tooltip engagement
- Time to first click
- Search usage
- Category usage
- Email signups
- Social referrals

The most important behavioral question is:

> Does the wire help readers discover more useful stories and click through to original reporting?

---

# 22. Acceptance Criteria

The product redesign is considered successful when:

- [ ] Homepage is visually cleaner without becoming more complex
- [ ] Mobile users can scan stories comfortably
- [ ] Every story has source attribution
- [ ] Categories are available
- [ ] Desktop tooltip works
- [ ] Mobile summary interaction works
- [ ] Archive is permanent and searchable
- [ ] RSS works
- [ ] Search works
- [ ] Core content exists in initial HTML
- [ ] Metadata and structured data are implemented
- [ ] Analytics measure outbound behavior
- [ ] Human approval remains mandatory
- [ ] Homepage remains a minimalist news wire
